**M2 is closed.** A message sent to self and reopened returns its real subject
(from the protected-headers tree), its body, and a signature that verifies
against the identity's own fingerprint. Decoding the ciphertext by hand confirms
the algorithms rather than trusting the UI: two **v6 PKESK** packets with
**1197-byte bodies** — a classical X25519 PKESK is ~120 bytes, ML-KEM-768's
ciphertext alone is 1088 — and a **SEIPD v2** payload under **AES-256-OCB**. So
it really is the RFC 9980 hybrid and not a silent fallback to the classical
subkey.

⚠️ **Nothing is committed.** All of this is in the working tree.

## 1. Rebuilding from clean

`app/android/` is gitignored and regenerated. The `.so` and generated Kotlin live
**inside the module** (`app/modules/cryptmail-core/android/src/main/`), so they
survive `prebuild --clean` — but they are gitignored too, so a fresh clone needs
steps 2–3.

```powershell
# 1. Native project
cd D:\Programs\mailer\app
npm ci
npx expo prebuild -p android

# 2. Cross-compile both ABIs into the module
cd ..\core
cargo ndk -t arm64-v8a -t x86_64 `
  -o ..\app\modules\cryptmail-core\android\src\main\jniLibs build --release

# 3. Bindings — from an Android .so, version-locked bindgen
cargo run --bin uniffi-bindgen -- generate `
  --library ..\app\modules\cryptmail-core\android\src\main\jniLibs\arm64-v8a\libcryptmail_core.so `
  --language kotlin --out-dir ..\app\modules\cryptmail-core\android\src\main\java

# 4. Build and run
cd ..\app
npx expo run:android
```

**Check:** the banner reads *"Real encryption, demo mailbox"* on its own.
`getNativeCore()` returning non-null flips `cryptoMode` to `real`; nothing is
configured by hand.

Metro on an emulator needs `adb reverse tcp:8081 tcp:8081`.

## 2. What to do next, in order

### 2.1 The Argon2id wrapping in Rust — ✅ done

A lost device is no longer a permanently lost identity. `core/src/recovery.rs`
re-locks the secret key — primary and every subkey — from the Keystore passphrase
to an **OpenPGP Argon2id S2K** derived from the recovery code, and back again on
restore.

The open decision in the earlier design is closed: rPGP 0.20 does expose
`set_password_with_s2k`, and Argon2id is already its V6 default (RFC 9106 choice
2 — 64 MiB, 3 passes, 4 lanes, AES-256-OCB). So the XChaCha20-Poly1305 fallback
was dropped along with the `argon2` dependency, the bespoke envelope, and the
"store the parameters in the blob" requirement — the S2K packet carries them.
**The blob is a standard armored OpenPGP secret key**, openable by GnuPG or
Sequoia with the code.

The "two generators must agree" trap was removed rather than managed: the code is
generated in TypeScript and passed down, so Rust never implements Crockford
base32. It normalises defensively (upper-case, `I`/`L`→`1`, `O`→`0`) and hashes
the bare 32 characters — grouping and case cannot cause a false "wrong code".

See [`superpowers/specs/2026-08-08-key-recovery-rust-design.md`](superpowers/specs/2026-08-08-key-recovery-rust-design.md)
and the plan beside it.

The test that matters: **a message encrypted to a key, whose device is then
destroyed, decrypts after restoring from the code on a fresh device with a
different Keystore passphrase** — and Bob's signature still verifies.
`cargo test` is 38, `npm test` 194.

Still open here: recovery is not part of first-run onboarding (see §0.15 of
[features.md](features.md)), and the blob is exported by hand rather than stored
as a self-addressed message, which waits on M3.

### 2.2 First-run wall — ✅ done

Two flaws together made mailing yourself impossible without knowing the trick.
Both are fixed:

1. Recipient resolution moved out of `AppState` into `app/src/state/recipients.ts`
   (pure, 8 tests). Our own address now resolves from the **identity**, not the
   keyring — which never contains it, and must not, since `upsertKey` would then
   be able to mark our own key `changed`. It resolves `verified`: there is no
   out-of-band comparison to make with yourself. A stale keyring entry for our
   own address cannot override it. `deliver` de-duplicates `recipientKeys`, so a
   self-addressed message still emits one PKESK for our key rather than two.
2. `pasteFromClipboard` in `KeysScreen` now reports both an empty clipboard and a
   read that throws, through the `Callout` already beside the field.

Note this does **not** put the identity in the keyring. It is not a contact; it
is resolved alongside one.

### 2.3 A physical phone

Everything so far is an emulator, which has no StrongBox — so
`KeystorePassphrase` has only ever run its **fallback** path. The StrongBox path
is still unexecuted. Both ABIs are already built and in `abiFilters`, so a phone
needs no config change: plug in and `npx expo run:android`.

Two phones are needed for the goal sentence (a real sender and recipient).

### 2.4 Google OAuth (M3/M4)

Independent of everything above.

**The redirect flow this section used to describe is gone.** It predicted a
`redirect_uri_mismatch` and suggested switching to the reversed-client-id scheme
(`com.googleusercontent.apps.<id>:/…`). That advice was wrong in a way no scheme
change fixes: Google refuses custom URI schemes from an Android OAuth client
outright, so `expo-auth-session` with `cryptmail://oauth` could never have
completed. `app/src/auth/googleAuth.ts` was rewritten on **Google Play services**
sign-in (`@react-native-google-signin/google-signin`), and `expo-auth-session`
was removed. See
[the design spec](superpowers/specs/2026-08-08-google-auth-native-design.md).

**What this costs.** Sign-in now requires Play services on the device. A
de-Googled Android build and the web build both lose it — `config.ts` detects
the missing module (`hasSignInModule`) and reports the downgrade through
`demoReason()` rather than claiming a mailbox it cannot reach. Recovering either
means a hosted redirect, which means running a server.

**Two console clients are needed**, and only one of them is named in code:

- an **Android** client for package `app.cryptmail.prototype` with the debug
  signing SHA-1 — never referenced in code; Play services matches it implicitly;
- a **Web** client, whose id goes in `app/.env` as
  `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`. This is the one the code uses, on Android.

```powershell
cp app\.env.example app\.env   # EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID=...
```

**Register the SHA-1 of the keystore Gradle actually signs with — not your
user-level one.** This is the trap that cost the most time here. Expo's prebuild
generates `app/android/app/debug.keystore`, and
[`android/app/build.gradle`](../app/android/app/build.gradle) points **both**
`debug` and `release` at it. `~/.android/debug.keystore` — the one every
`keytool` snippet on the internet names, and the one this document named until
2026-08-08 — signs nothing in this project.

Getting it wrong fails as `DEVELOPER_ERROR` (status 10) *after* an account is
chosen, which reads like a code bug and is not.

| Keystore | SHA-1 | Used? |
|---|---|---|
| `app/android/app/debug.keystore` | `5E:8F:16:06:2E:A3:CD:2C:4A:0D:54:78:76:BA:A6:F3:8C:AB:F6:25` | **Yes — register this** |
| `~/.android/debug.keystore` | `AD:CC:27:38:68:34:50:AE:D7:53:A4:C1:76:74:35:DF:55:FF:81:DA` | No |

Ask the APK rather than a keystore, since the APK is the thing Google checks:

```powershell
& "$env:LOCALAPPDATA\Android\Sdk\build-tools\36.1.0\apksigner.bat" verify `
  --print-certs app\android\app\build\outputs\apk\debug\app-debug.apk
```

`app/android/` is gitignored and regenerated by prebuild, but Expo's template
keystore is deterministic, so this fingerprint is stable across machines and
rebuilds. A **release** build signs with the same debug key today — fine for a
prototype, wrong for a shipped one, and it needs its own client entry when that
changes.

**The scope decision was reversed on 2026-08-08.** This section previously
recorded `gmail.readonly` + `gmail.send` as "a deliberate least-privilege
choice, not an oversight". That choice was overturned, not merely restated:
`updateFlags` calls `messages.modify`, so star, mark-read and archive — all
built, shipped UI — would have 403'd. `config.ts` now requests `openid`, `email`
and **`gmail.modify`**. The cost is honest: `gmail.modify` reads on the consent
screen as permission to change and delete mail, which is broader than the app
needs for anything but flags. It is chosen up front because raising it later
forces every user to re-consent.

### 2.5 Background scheduler (§7.3)

out with the app closed. Needs `expo-background-task` / `expo-task-manager`.
Deferred until now because it cannot be verified without a device — that
objection has expired.

## 3. Traps this build actually hit

Five defects, **none in the cryptography** — all in the bridge or the build,
which is where the risk always was. Recorded so they are not re-learned.

1. **Expo modules are not in `NativeModules`.** `getNativeCore()` looked the
   module up in React Native's legacy registry; the Kotlin registers with
   `expo-modules-core` and is reached via `requireOptionalNativeModule`. It
   failed *silently* — the core was installed and working while the app reported
   "not wired up yet". **And the tests passed the whole time**, because they
   registered their fake in `NativeModules` too: a green suite over a bridge that
   could not work. `getNativeCore(bridge?)` now takes the module as a defaulted
   parameter, because `expo-modules-core` exports through getters that neither
   `jest.spyOn` nor a module factory can replace.

2. **A Fabric assertion killed the app on every send.** `usePressScale`'s style
   was applied as `off ? undefined : press.style`, so a button going `busy`
   removed the `transform` array from a view the native animation driver still
   held — and `SurfaceMountingManager.overridePropsReadableMap` asserts on
   exactly that, fatally, on the main thread. The Send button sets `busy`
   mid-flight. **Never make an animated style conditional**; `Pressable`'s own
   `disabled` already stops the animation.

3. **Generated artefacts must live in the module, not `app/android/`.** They were
   written into the `:app` module, where `:cryptmail-core` cannot see them
   ("Unresolved reference 'uniffi'") — and pointing `java.srcDirs` there instead
   would define the class twice. `app/android/` is also deleted by
   `prebuild --clean`, which would have silently removed the crypto core.

4. **`versionCode`/`versionName`** are required in the module's `defaultConfig`
   or `expo-module-gradle-plugin` fails configuration outright.

5. **The module cannot compile before the bindings exist.** To get a blank app on
   a device first — worth doing, it separates toolchain failures from core
   failures — rename `expo-module.config.json` aside so autolinking skips it,
   re-prebuild, then rename it back. Forgetting to restore it means the core
   silently never links.

Also: the **16 KB page-size dialog** on launch lists every library including
React Native's own. It is a generic dev-build warning, not ours; the app runs in
compatibility mode.

## 4. Limits, not tasks

Do not "fix" these; they are decisions with reasons recorded.

- **Signatures are not quantum-safe.** Stage 1 signs with Ed25519 deliberately —
  a signature forged in 2040 does not retroactively compromise a message sent
  today, whereas harvested ciphertext does. See [post-quantum.md](post-quantum.md).
- **Two implementations agreeing is not conformance.** Sequoia and rPGP could
  share a misreading of RFC 9980. No third implementation exists to ask.
- **The interop harness exchanges the inner payload**, not the PGP/MIME envelope.
  `mime.ts` has now been produced *and* parsed by the real core on a device, but
  never by another client. A conformance suite against Thunderbird/Proton/GnuPG
  is Tier 4 in [features.md](features.md).
- **There is no backend, and recovery does not need one.** The server in
  [key-management.md](key-management.md) is zero-knowledge, so it only ever
  bought convenience. The next increment is storing the backup blob as a
  self-addressed message in the user's own mailbox — no new infrastructure.
- **Metadata is not protected.** Sender, recipients, timestamps, size stay visible.
- **Web will never encrypt for real.** A Kotlin module cannot load in a browser,
  and `expo-secure-store` has no browser implementation, so the web build keeps
  its device key beside the data it protects. `storageReason()` reports this.

## 5. Ground rules

From [CLAUDE.md](../CLAUDE.md), restated because they are the easiest to erode:

1. **No plaintext downgrade, ever.** No key, or a changed fingerprint → sending
   and scheduling fail with an explanation.
2. **The demo core is not crypto.** Never remove the `kind: 'demo'` reporting or
   the banners that surface it.
3. **Nothing crosses the core boundary but strings**, and a private key never
   comes back.
4. **Screens never call providers or the core directly** — everything goes
   through `AppState`.
5. **Docs are the source of truth.** A change that contradicts a doc updates the
   doc in the same PR, or does not land.
