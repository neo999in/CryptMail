# cryptmail-core

The crypto half of the `CryptCore` contract in
[`app/src/core/types.ts`](../app/src/core/types.ts). Post-quantum hybrid
encryption per RFC 9980, built on rPGP.

```bash
cargo test        # 27 tests, no Android toolchain required
```

## What it does, and what it deliberately does not

**Does:** hold the private key, generate identities, import contact keys,
encrypt-and-sign, decrypt-and-verify.

**Does not:** build or parse MIME. [`app/src/core/mime.ts`](../app/src/core/mime.ts)
already implements [`docs/message-format.md`](../docs/message-format.md) and is
covered by tests. Reimplementing it here would duplicate the fiddliest part of
the envelope and risk two divergent implementations of the same spec — the plan
even warns that rPGP does crypto, not MIME, so this would all be hand-written.

So the split is: **TypeScript composes the envelope, Rust does what must not
happen in JavaScript.** Plaintext crosses the boundary — it always did, since
`parseEncrypted` returns a decrypted body — but the private key never does.

## Algorithms

Stage 1 of [`docs/post-quantum.md`](../docs/post-quantum.md):

| | Algorithm | Why |
|---|---|---|
| Primary (sign, certify) | Ed25519 | Classical. PQ signatures inflate the cert to ~18 KB, which Autocrypt cannot carry on every message. |
| Encryption subkey | **ML-KEM-768 + X25519** (RFC 9980, id 35) | Post-quantum confidentiality. Composite: an attacker must break both. |
| Symmetric | AES-256 OCB, SEIPDv2 | |
| Key version | V6 | Required by RFC 9980. |

Certificates come out at ~2.4 KB. Stage 2 (ML-DSA-65 primary) is deferred; see
that document for why the two are staged apart, and [`spike/pqc-rpgp`](../spike/pqc-rpgp)
for the measurements.

## Invariants, each with a test

1. **A private key never appears in a return value.** Exit criterion 4 of
   [`docs/prototype-plan.md`](../docs/prototype-plan.md), and the whole reason a
   native core exists rather than OpenPGP.js.
2. **Secret keys are S2K-encrypted at rest** under a passphrase the caller
   supplies. On Android that comes from the Keystore.
3. **An unintended recipient cannot decrypt**, even holding a valid key of their
   own.
4. **`unknown` and `invalid` signatures stay distinct.** Collapsing them would
   let a forged message read as merely unverified.
5. **A signature from the sender's signing subkey verifies.** Most OpenPGP
   clients sign with a subkey rather than the primary; checking only the primary
   reports them as forged. See [Interop](#interop) — that is where it came from.

## The UniFFI surface

`src/ffi.rs` is a real UniFFI interface: `uniffi` 0.32 is a dependency,
`CryptMailCore` is a `#[derive(uniffi::Object)]` with an `#[uniffi::export]`
impl block, and `lib.rs` calls `uniffi::setup_scaffolding!()`.

Generating the Kotlin bindings is **verified on the host**:

```bash
cargo build --lib
cargo run --bin uniffi-bindgen -- generate \
  --library target/debug/libcryptmail_core.so \
  --language kotlin --out-dir <somewhere>
```

That produces a `CryptMailCoreInterface` carrying exactly the five methods in
[`app/src/core/nativeCore.ts`](../app/src/core/nativeCore.ts) — `loadIdentity`
nullable, `decryptVerify` taking no address — plus a `constructor(storageDir,
passphrase)`.

The bindgen is a `[[bin]]` in this crate rather than `cargo install
uniffi-bindgen` on purpose: that installs whatever is newest on crates.io, and
scaffolding built by one `uniffi` version with bindings generated by another
produces Kotlin that compiles and then misreads the FFI at runtime.

Errors cross as a sealed `FfiException` with one subclass per `CoreError` code,
carrying the `Display` string as its message (that is what `#[uniffi(flat_error)]`
buys). So the Kotlin mapping onto the TypeScript `CoreError` union is a `when`
over types the compiler checks exhaustively, not a string comparison.

## Building for Android (M2)

Not yet done, and not doable without an Android SDK/NDK — neither command below
has been run.

```bash
rustup target add aarch64-linux-android x86_64-linux-android
cargo install cargo-ndk

# Cross-compile. Both ABIs, matching `abiFilters` in the Expo module's
# build.gradle — arm64 for phones, x86_64 for the desktop emulator.
cargo ndk -t arm64-v8a -t x86_64 -o ../app/android/app/src/main/jniLibs build --release

# Then regenerate the bindings from the *Android* .so
cargo run --bin uniffi-bindgen -- generate \
  --library target/aarch64-linux-android/release/libcryptmail_core.so \
  --language kotlin --out-dir ../app/android/app/src/main/java
```

Pin the NDK version. Cross-compilation is historically the biggest time sink in
this project, which is why `prototype-plan.md` puts it in M0 while the Rust
surface is trivial.

### The Kotlin module

Written, at
[`app/modules/cryptmail-core/`](../app/modules/cryptmail-core) — an Expo local
module registered as `CryptMailCore`, exposing the five methods in
[`app/src/core/nativeCore.ts`](../app/src/core/nativeCore.ts). It:

- Unwraps a passphrase from the **Android Keystore** and passes it to
  `CryptMailCore::new` once, at construction. The passphrase never appears in a
  JavaScript-visible signature — that is the point of the native core.
- Uses app-private storage for `storage_dir`.
- Maps the `FfiException` subclasses onto the `CoreError` codes TypeScript
  already switches on. The `when` is exhaustive over a sealed class, so a new
  variant on this side becomes a compile error there rather than an unhandled
  code at runtime.
- Runs every call off the main thread; keygen takes a noticeable moment.

Note `decryptVerify` takes **no** email argument. The envelope cannot say which
identity to decrypt with — our address may be in `Cc`, or `To` may list several
people — so the core uses the identity it holds
(`Core::stored_identity_email`).

> ⛔ **Never compiled.** There is no Android toolchain in the environment this
> was written in. Its README lists the parts most likely to need adjusting on a
> first build.

## Interop

Every test *in this crate* is rPGP talking to itself, which is why
[`spike/interop-rpgp-sequoia`](../spike/interop-rpgp-sequoia) exists: it
round-trips messages against **Sequoia-PGP**, an implementation independent of
rPGP in authorship, parser and primitives. All 9 checks pass in both directions.

That harness found a defect no test here could have: the core signs with its
Ed25519 primary, so `verify()` only ever checked primaries — and reported
signatures from a sender's **signing subkey** (what Sequoia, GnuPG and Proton
all use by default) as `invalid`, which the UI renders as forged. Fixed, and
pinned by `tests/foreign-signature.rs`.

It does not prove everything: two implementations can share a misreading of the
RFC, and there is no third to ask. The old "cross-check against GnuPG" step from
M1 remains impossible until GnuPG ships post-quantum.
